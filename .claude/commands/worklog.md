# /worklog — 작업내역 기록

지금까지의 작업 상황을 `.ai/` 아래에 기록한다. `.ai/`는 gitignore 대상이라 커밋되지 않는다 —
**새 채팅이 과거 작업을 복원하는 유일한 통로**이므로, 나중의 나(또는 다른 에이전트)가 읽는다고 생각하고 쓴다.

입력: `$ARGUMENTS` (비어 있으면 대화 맥락에서 작업 슬러그를 직접 정한다)

## 1. 기록 대상 파악

먼저 아래를 실제로 확인한다. 기억이나 추측으로 쓰지 않는다.

```bash
git status --short && git branch --show-current && git log --oneline -10
```

```bash
git diff --stat && git diff --cached --stat
```

`.ai/` 디렉터리가 없으면 `.ai/worklog/` 까지 만든다.

## 2. 작업 슬러그 결정

- `$ARGUMENTS`에 슬러그가 있으면 그것을 쓴다.
- 없으면 현재 브랜치명 또는 변경 내용에서 kebab-case 슬러그를 만든다 (예: `search-palette-a11y`).
- **같은 작업이면 파일을 새로 만들지 말고 기존 파일에 이어 쓴다.** `.ai/worklog/`를 먼저 뒤져 볼 것.

## 3. 세션 로그 작성 / 갱신

`.ai/worklog/<YYYY-MM-DD>-<슬러그>.md`

날짜는 추측하지 말고 확인한다:

```bash
date +%Y-%m-%d
```

파일이 이미 있으면 맨 아래에 `## <HH:MM> 추가 진행` 섹션을 덧붙인다. 형식:

```markdown
# <작업 제목>

- 슬러그: <slug>
- 브랜치: <branch>
- 시작: <YYYY-MM-DD>
- 상태: 진행중 | 검증대기 | 완료 | 보류

## 목표

<무엇을 왜 하는지 2~4줄. 사용자가 말한 요구사항을 그대로 남긴다.>

## 변경한 것

- `apps/croffle-blog/app/components/search-palette.vue` — <무엇을 어떻게>
- `packages/directus-blog-core/src/queries/post.ts` — <무엇을 어떻게>

## 결정과 근거

- <선택한 방식> — <왜 이걸 골랐는지, 버린 대안은 무엇인지>

## 검증 결과

<AGENTS.md §5 순서로 실제 실행한 것만. 안 돌렸으면 "미실행"이라고 쓴다.>

- `pnpm lint` — 통과 / 실패(내용)
- `pnpm --filter @croffledev/directus-blog-core build` — ...

- <다시 밟지 않아야 할 지뢰, 재현 조건, 환경 요구사항(.env 등)>
```

## 4. `.ai/state.md` 갱신

`.ai/state.md`는 **현재 상태 스냅샷 한 장**이다. 여러 작업을 누적하지 말고 항상 덮어쓴다.
`/spec`이 가장 먼저 읽는 파일이다.

```markdown
# 현재 상태

- 갱신: <YYYY-MM-DD>
- 브랜치: <branch>
- 진행중 작업: <slug> → `.ai/worklog/<파일명>`
- 한 줄 요약: <지금 무슨 상태인지>

## 지금 바로 이어서 할 일

1. <액션>
2. <액션>

## 미커밋 변경

<git status --short 결과 요약. 없으면 "없음">

## 열린 질문 / 사용자 확인 필요

- <있으면. 없으면 "없음">

## 관련 문서

- `.ai/worklog/<파일명>`
- `.ai/specs/<있으면>`
```

## 5. 규칙

- **사실만 쓴다.** 검증을 안 돌렸으면 "미실행", 실패했으면 실패 내용을 그대로 남긴다. 통과했다고 꾸미지 않는다.
- 코드를 그대로 복붙하지 않는다. 파일 경로 + 무엇이 바뀌었는지로 충분하다. 코드는 git에 있다.
- 비밀값(Directus 토큰, 배포 키, `.env` 실값)은 절대 적지 않는다.
- 완료된 작업의 로그는 지우지 말고 `상태: 완료`로 바꾼다. `.ai/state.md`에서만 내린다.
- 기록만 하고 커밋/푸시하지 않는다.

마지막에 작성/갱신한 파일 경로를 사용자에게 알려준다.
